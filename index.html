Operating-system direction

SenseOS

A computer environment designed around one coherent surface and clearly bounded system behavior.

The role

SenseOS is intended to provide the system foundation: starting the computer, managing programs, files, and devices, and presenting a consistent workspace.

Work so far

Prototype work has tested parts of boot handoff, persistent storage, program admission, filesystem access, capability checks, and interface input. These are partial paths, not a complete or production-ready general-purpose operating system.

One shared object space

The current Rust-Sense design gives objects stable identities and typed interfaces; filesystem paths bind names to those objects, making the filesystem one projection of shared system state. The object model includes data, devices, processes, services, buses, and network endpoints or connections. A journal records state transitions, while authorization remains a separate check. This is an implemented architectural foundation in the reviewed source, not a claim that every object provider is complete.

Where the network fits

This model gives a remote resource a natural place in a shared namespace: a future adapter could expose authenticated remote objects through explicit bindings and scoped rights. The reviewed source does not yet implement a complete network filesystem transport, peer authentication, or remote operation flow. That is the next architectural seam to prove, not a current capability.

Compatibility, in stages

The long-term goal is to run applications from many operating-system families through SenseOS services and the SenseUI surface. Existing syscall catalogs are research inventories, not application compatibility. In the reviewed Linux x86_64 route, only write, exit, and exit_group are handled; unsupported calls return ENOSYS. No AI syscall translator or general foreign-app runtime is implemented. Progress needs explicit profiles for each ABI, architecture, binary format, runtime, and app framework, with deterministic adapters and real application tests. AI may help draft those adapters; typed contracts, authority checks, and validation must govern execution.

How it relates

SenseOS is intended to host the shared SenseUI surface as native system userspace. Other operating systems would open the same surface as a web app, so content can move across environments without changing the interface. This remains a product direction; this website is not a running SenseOS system.

One surface across devices

SenseUI

A shared visual workspace that aims to make different tools and content feel like one environment.

The direction

SenseUI is being developed around Rust-Sense as a declarative language for a common surface. The goal is for one interface to stay familiar while its projected content adapts across web, mobile, and SenseOS, so users do not feel they have switched mediums.

Project lineage

SenseUI carries forward the Rust UI work explored under the earlier AchetUI and Uni-UI names. SenseUI is the current name for the shared-surface product direction; the older names describe project history, not separate finished products.

From declarations to Rust-Sense

Rust-Sense grew from the declarative work behind SenseUI. The founder's vision is for it to become a standalone, Rust-derived language: its own defined syntax, intent model, and toolchain, designed to carry explicit human-approved intent, permissions, and machine-checkable contracts from firmware and kernels through interfaces and web apps. A proposed next milestone is a small language slice with mandatory contracts for its verified profile, then a Sphere mirroring path that emits a proof-carrying executable artifact checked against that language's semantics. The goal is a compile-free user workflow, not a claim that translation disappears: producing executable output still requires a semantics-preserving implementation. A successful mirror or round trip alone does not prove correctness; the contract must match approved intent, translation must be proved to preserve it, and an independent checker must validate the evidence. AI could draft implementations and proofs, but it cannot approve intent or certify its own claims. Verus is a candidate verifier for a carefully bounded Rust subset, not the language identity. This is a direction, not a current compiler, Sphere integration, or end-to-end proof; hardware and unverified-code boundaries would need explicit treatment.

The language ambition

The design target is to express structure, styling, interaction, and 3D scenes together, including a planned Three.js-compatible browser path, with standard web markup generated for non-SenseOS environments. R16 tests source generation only; it does not provide a general 3D renderer or a universal native runtime.

About DarkBlaze Group

People, purpose, and the work ahead.

I began BlackBlaze in 2011 as a graphic design group, creating websites and corporate identities. After working in real estate, I moved into neural-network design, research, and engineering, then restarted the group as DarkBlaze in 2025. That path led me to formal-verification experiments, including working models of seL4 and Muen and a BIOS-to-Qwen 2.5 handoff on a laptop.

DarkBlaze is now an independent, early-stage technology initiative exploring how computing can express intent, respect declared limits, and remain coherent across devices. The projects take different routes into that question, from a shared interface to systems research and machine-learning design.

At DarkBlaze, we ask how computing can be made as precise and verifiable as the laws that shape the natural sciences.

HNDEN

HNDEN is our first-generation neural network design prototype: a spark of vision for systems whose relationships and changing activity can be understood as one connected whole.

The prototype

This page presents the first generation of our neural network design idea. The moving field makes its central intent visible: explore how connected elements and their relationships could be considered together. It is an early design prototype, not a claim of a complete or validated neural network.

How it works as an idea

At a concept level, the design treats the network as a connected field. Changes among parts should be expressible in the wider pattern, so the system can preserve context as activity shifts. The motion is illustrative and does not document the implementation.

What we plan to build

Our plan is to turn the design into a measurable working prototype, validate its behavior, and test efficient execution across edge devices and larger compute. That requires dedicated engineering time and meaningful compute access.

Rosetta + 0xAlexandria

Sphere

Intent-driven mirroring: compile and decompile between bounded representations while keeping the declared goal and evidence in view.

What mirroring means

Sphere's current scope is JSON, Rust, and raw-machine representations. Within supported profiles, it explores compiling from declared intent into a target form and mirroring a supported form back for comparison, reducing dependence on writing every target syntax by hand. Each route is intent-driven, bounded, evidence-checked, and must refuse work it cannot support.

The larger implication

The design idea is not tied to one programming-language syntax. If a language can be calibrated against explicit intent and its output verified within declared bounds, the same compile-and-mirror loop could extend to it. We call this direction syntax-independent or language-independent mirroring. Broader language coverage is a research goal, not a current capability; it does not promise arbitrary code generation, zero translation effort, or lossless reversal.

Why it matters

If this direction matures, software builders and AI-assisted tools could make low-level choices easier to inspect, compare, and constrain. That could have wide consequences for portability and accountable automation. It is a research opportunity, not a current guarantee of safe or correct output.

One programme

Sphere is the umbrella effort. Rosetta explores structured translation between intent and target-specific representations; 0xAlexandria organizes machine-readable instruction profiles with their sources, scope, and evidence. They are parts of one effort, not separate products on this site.

Where it stands

There are working components and bounded, independently checked examples, but they cover selected forms and targets. Sphere is not a general-purpose compiler, a complete catalogue of every processor, or an end-to-end proof that generated programs behave as intended.

What support can unlock

Focused engineering, stronger target coverage, independent comparison against trusted tools, and end-to-end validation could show where the approach is useful and where it must refuse unsupported work.

Privacy notice

This notice describes the current R16 browser surface. Hosting-provider logging and retention have not been verified.

Information handled by this page

This static site does not run analytics, set tracking cookies, save browser storage, or create application-level visitor or interaction logs. The local clock uses your device time; theme choices stay in memory for this visit. When you use the live Site Secretary, your message (up to 240 characters), up to eight prior turns (1,200 characters per turn), and up to 12,000 characters of relevant site excerpts are sent through a Cloudflare Worker to OpenRouter and the selected model provider to generate a reply. The deployed model is Cohere North Mini Code (free) through OpenRouter. The site does not retain the conversation; Cloudflare, OpenRouter, and the model provider may process request data under their own policies. Conversation context stays in page memory and is cleared when you clear it or leave/reload the page. This R16 build does not yet include a weather service and does not request location. When local weather is added, the browser must ask for location only after you choose that feature, and the notice must name the weather provider and explain that it receives the coordinates.

Contact handoffs

The Site Secretary keeps recent conversation in page memory for this visit, and you can clear it at any time. If you choose an email handoff, your email app opens a draft with the details you selected; nothing is sent until you review and send it. Choosing WhatsApp passes the prepared reply to WhatsApp. The site does not receive or retain either handoff.

Connection data and hosting

The website code does not implement application-level IP logging or send IP addresses to analytics. The web host, CDN, DNS, or network providers may still process connection data. Their logging and retention practices have not been verified; this notice cannot promise that no provider records an IP address.
